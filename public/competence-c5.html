Preuve 01 / 03 — SAE S3, Janvier 2026

MyPulse — Conduite de projet multi-livrables

Pilotage d'un projet web en binôme avec production de trois livrables simultanés : Rapport Final (architecture), Rapport Qualité (risques, CI/CD), Rapport Juridique (RGPD, PI, CGU) — en parallèle du développement de l'application.

Gestion de projet MVP agile Analyse des risques Documentation

Contexte et ressources mobilisées

SAE S3 — développer une plateforme de vote musical et produire trois rapports complémentaires dans un délai contraint. Cours mobilisés : méthodes agiles (Scrum, MVP), gestion des risques, qualité logicielle, droit du numérique (RGPD).

Activités et implication

  • Planification agile : définition de 2 MVPs incrémentaux (MVP1 vote basique / MVP2 social + gamification), priorisation par valeur utilisateur et faisabilité, choix de stack justifié
  • Matrice des risques QA : 6 risques identifiés (bugs non détectés — critique ; corruption de données — critique), chacun avec impact, probabilité et mesure préventive
  • Feuille de route qualité : recommandations PHPUnit, CI/CD GitHub Actions, GitHub Wiki, Trello, Lucidchart
  • Rapport juridique : cartographie RGPD (3 catégories de données), mentions légales, CGU, politique de confidentialité opérationnelle

Apprentissages clés

  • Gestion multi-livrables : les trois rapports sont interdépendants — une incohérence entre l'architecture technique et les mesures RGPD annule les deux
  • Anticipation des risques : matrice en amont plutôt que réaction quand ça casse
  • Documentation comme actif : les 3 rapports (24 + 8 + 14 pages) constituent une base de connaissance pour la maintenance future

Rapport juridique (14 pages)

RGPD, propriété intellectuelle, CGU et politique de confidentialité rédigées et opérationnelles.

Preuve 02 / 03 — Stage CENCA, 2025-2026

Stage CENCA — Développement de nouvelles fonctionnalités sur l'existant

Développement de nouveaux modules Angular sur l'application Atlas (CENCA) en partant d'une architecture existante. Chaque fonctionnalité est personnalisée selon les besoins réels des utilisateurs (géomaticiens, personnel administratif) — ce qui impliquait de comprendre les contraintes métier avant de coder.

Angular Node.js Architecture existante Besoins utilisateurs

Contexte et ressources mobilisées

CENCA — l'application Atlas existait déjà avec une architecture Angular définie. Ma mission : ajouter de nouveaux modules (gestion des actes notariaux, des parcelles cadastrales, des actes multi-sites) en restant cohérent avec le code existant. Vocabulaire métier spécifique à appréhender : foncier, cadastral, actes notariaux, gestion des espaces naturels.

Activités et implication

  • Analyse de l'existant : lecture et compréhension de l'architecture Angular déjà en place avant de développer — pour rester dans la même logique de composants, services et modules
  • Compréhension des besoins : les fonctionnalités devaient correspondre aux usages réels des géomaticiens (gestion spatiale) et du personnel administratif (gestion foncière et documentaire)
  • Module Actes (MFU) : gestion des actes notariaux liés aux sites naturels, avec auto-complétion cadastrale et lien aux parcelles
  • Module Parcelles cadastrales : intégration des données IGN/cadastre pour identifier et lier les parcelles aux sites CENCA
  • Actes multi-sites : interface permettant de lier un acte à plusieurs sites simultanément — contrainte non prévue dans l'architecture initiale, nécessitant une adaptation

Apprentissages clés

  • Partir de l'existant exige plus de rigueur que de partir de zéro : chaque choix doit s'aligner avec ce qui est déjà là, sans le casser
  • Comprendre le métier avant de coder : les termes «foncier», «cadastral», «acte notarial» ne sont pas interchangeables — une confusion dans le modèle se retrouve dans l'interface
  • Personnalisation selon les profils : géomaticien ≠ personnel administratif — même donnée, représentations et workflows différents

Application métier Angular développée pour les géomaticiens et le personnel administratif du Conservatoire d'espaces naturels de Champagne-Ardenne.

Preuve 03 / 03 — Stage professionnel, 2025-2026

Rapport de Stage — Capitalisation d'un projet professionnel

Rapport de stage de 37 pages formalisant les choix techniques, l'architecture et les retours d'expérience. Communication formelle adaptée à plusieurs types de lecteurs : technique, exécutif, maintenance future.

Rapport technique Documentation Retour d'expérience

Contexte et ressources mobilisées

Stage professionnel — produire un rapport de 37 pages synthétisant le travail de stage pour plusieurs audiences : directeur technique (vue stratégique), équipe de maintenance (détails d'implémentation), jury académique. Contrainte : confidentialité partielle des données métier.

Activités et implication

  • Documentation des choix techniques : chaque décision d'architecture justifiée par les contraintes du contexte (performances, maintenabilité, délais, compétences équipe)
  • Diagrammes d'architecture : flux de données, interfaces entre composants — rendre le système compréhensible pour un développeur qui reprend le projet
  • Retours d'expérience : ce qui a fonctionné, les difficultés rencontrées, les ajustements de méthode en cours de projet
  • Recommandations priorisées : liste d'améliorations techniques et organisationnelles pour l'équipe après le départ du stagiaire

Apprentissages clés

  • Adapter la communication au public : même contenu, niveau de détail différent selon le lecteur (stratégique vs. opérationnel)
  • Documenter pendant le projet, pas après : reconstruire le raisonnement a posteriori est plus difficile et moins fidèle
  • La valeur d'un projet = code livré + documentation permettant à d'autres de le maintenir
